Lists and floating fields

Automatic Word list labels are reconstructed for decimal, alphabetic and Roman numbering. Leading marker punctuation and spacing do not count as a wording change; the actual number, letter and clause still do. List additions are proposed only where a clear, ordered neighbouring list provides a match.

Supported new items reuse an XDP paragraph or existing plain-text list. Separate draws can be cloned only inside top-to-bottom flowed subforms. Positioned additions are shown but blocked for Designer placement. Any required renumbering must also be approved.

Recognised Word data fields and XFA embedded floating fields appear as protected ⟦FIELD:1⟧ slots. Saved field display values do not become static text. Compare surrounding wording; field counts and order must agree. Bindings are not verified by field names. Literal placeholder recognition can be disabled.

Create XDP from Word

Switch modes and select only a DOCX. Keep rich formatting, source page geometry and intact paragraphs enabled for closest fidelity, then build the preview. Word headings become named sections. Optional splitting uses sentence or word boundaries but introduces new line boundaries and is flagged as a layout loss. Each text object has an editable content label and unique, XML-safe name. The limit counts JavaScript UTF-16 text units, including protected markers.

Recognised field occurrences become separate hidden, blank, unbound text fields with inline XFA references. Configure their real bindings, types and calculations in Designer. Source font names, sizes, bold/italic, supported underlining, strike, colours, superscripts/subscripts, alignment, indents, tabs and spacing are mapped to XFA. Font files are not embedded. Tables, images and complex layout features are not reproduced and trigger a fidelity warning. Included headers, footers and notes appear as appended sections, not repeated page content.

Fidelity report and draft export

The report separates detected losses from renderer-verification notes. Known losses block XDP export until you explicitly allow a draft. This does not block exporting the report or object map. A report with no detected losses is not proof of visual identity: Word and Adobe rendering must still be compared. Superscript metrics, multiple line spacing and font substitution can affect appearance. Existing-XDP comparison remains wording-only; it does not import Word styling into an existing form.

Export and validate

Comparison exports patch guarded source positions rather than rewriting the whole template. JSON saves a review; CSV exports the change list. Generated templates have their own JSON object/source map; it is documentation, not an import format. Save any files before closing this in-memory session.

Open exported templates in your Adobe Designer workflow to check wrapping, overflow, page breaks, formatting and runtime behaviour. XML well-formedness and text checks are not Adobe schema or rendering validation. Signed/encrypted comparison targets cannot be exported.

Stable recurring mappings

A Word content-control tag xdp:OBJECT_ID can link one paragraph to one unique XDP text block. For generated objects, the map records their IDs. A paragraph split across several objects cannot use a single owner ID to map all parts automatically; re-splitting or manual mapping may be needed.

Local processing

The HTML embeds all JavaScript and CSS. No server, installation, network request or upload is needed. Open it in a current desktop Chrome or Edge browser that permits local HTML, file selection and downloads. Source files and reports can contain confidential text; protect the exports accordingly.
